# 記事を「読むコンテンツ」から「変化を前に進めるプロダクト」へ

> 対象：`/areas/[id]/[slug]`（記事詳細・現在55本）
> 目的：SEO/GEO で流入したユーザーが「読んで理解して終わる」構造を、
> 「次に何をやるかが分かって、実際に次へ進む」構造に変える。
> 制約：タイトル構造・見出し・FAQ・内部リンク・情報量は変更しない（検索評価を落とさない）。

---

## 0. 先に、いちばん重要な設計判断

### 「Step 3 / 全7ステップ」は、記事の属性ではない

ご要望の表示を素直に実装すると、記事データに `step: 3` を持たせたくなります。**これはやってはいけません。**

理由は、既に `/areas` で確定した構造にあります。1本の記事は複数の目的に属します。

| 記事 | 婚活ロードマップ | 仕事ロードマップ | 結婚式ロードマップ |
|---|---|---|---|
| 「眉を整えるだけで、印象は変わる」 | Step 2 / 7 | Step 3 / 6 | Step 4 / 8 |
| 「清潔感は『作れる』— 要素で分解する」 | Step 1 / 7 | Step 1 / 6 | Step 2 / 8 |

**ステップ番号は「記事の属性」ではなく「目的 × 記事の関係」です。**
記事に静的な数字を持たせた瞬間、他の目的から来た人には嘘になります。

### したがって、真実の置き場所はロードマップ側

```
lib/roadmaps.ts    ← 唯一の真実。目的ごとに「記事の並び」を持つ
   ↓ 参照
記事ページ          ← 何ステップ目かは、表示時に文脈から解決する
```

```ts
export type RoadmapStep = {
  slug: string;        // どの記事か
  impact: 1|2|3|4|5;   // この目的での効き（★の本数）— 編集判断
  task: string;        // 読んだあとにやること。1つだけ
  taskMinutes: number; // そのタスクの所要
};

export type Roadmap = {
  id: OccasionId;      // 既存の Job（romance / bigday / work / family / restart / gift）
  label: string;       // 「婚活ロードマップ」など、表示用の名前
  steps: RoadmapStep[];
};
```

- **ステップ番号** = `steps` 配列の index + 1（`全N`= 配列長）
- **★優先度** = `impact`。順番から機械的に導出せず、**編集判断として明示的に持つ**
  （「土台だから★5」は多くの場合正しいが、常に正しいとは限らないため）
- **所要時間** = 本文の文字数から自動算出（400字/分・切り上げ）。**手入力しない**
- **次の実践タスク** = `task`。ここがないと「③ 記事末尾」が作れない

### 文脈（どの目的で読んでいるか）の解決順序

```
① URL パラメータ  /areas/hair/aga-self-check?goal=bigday   ← 記事一覧・LP・広告からの遷移
② 直近の選択      localStorage の hr_goal                   ← 前に選んだ目的
③ 記事の既定値    その記事が最も効く目的（roadmaps から逆引き）
④ 不明           → ⑤ の目的取得UIを出す
```

**`?goal=` は表示のためだけに使い、canonical は素のURLのまま**にします。
既に `alternates.canonical` があるので、パラメータ付きURLがインデックスされることはありません。

## ② 各改善の理由

### S2 ロードマップ・ヘッダー ─ 「自分は今どこにいるのか」を最初の3秒で

**解く問題**：検索から来た人は、サイトの構造を知りません。1本の記事が孤立して見えるので、読み終わったら帰るしかない。

**効く理由**：
1. **未完了の可視化**（Zeigarnik効果）。「3/7」を見た瞬間、残り4つが気になる状態が作られる
2. **投資の初期化**。ここで初めて「自分はプロジェクトの途中にいる」という自己認識が生まれる
3. **期待値の提示**。「読了3分／実践15分」を先に出すと、読み切る確率が上がる

**★を編集判断にする理由**：順番から自動生成すると、後半のステップが一律で★2〜3になります。しかし「服のサイズ」は婚活では終盤でも効きは大きい。**効きと順番は別の軸**なので、`impact` を明示的に持ちます。

**「目的を変える」を必ず置く理由**：推定が外れたときに逃げ道がないと、ヘッダー全体が「見当違いの押しつけ」になります。1タップで直せる状態にしておく。

---

### S9 マイクロ・チェックポイント ─ 「今すぐ相談」を本文から撤去する

**解く問題**：現在、`guide` 記事の本文前に `InlineConsult`（今すぐ相談）が入っています。**まだ何も理解していない段階で商談を求めている**状態です。この位置のCTAはCVRに寄与せず、読了率を下げます。

**代わりに置くもの**：**その場で完了できる、2分以内の行動を1つだけ**。

```
✓ ここまでで、やることは1つ
  鏡で、眉頭の位置だけ確認する（2分）
  ［あとでやる］  ［できた］
```

**効く理由**：
1. **小さな完了の獲得**。1つでも「できた」を押すと、その人は読者から実行者に変わる
2. **コミットメントの一貫性**。実行者になった人は、次のステップへ進む確率が上がる
3. **相談の質が上がる**。1つでも試した人の相談は具体的になり、成約率が変わる

**「あとでやる」を並置する理由**：押せる選択肢が1つしかないと、押さない人は何も残さず離脱します。「あとでやる」も**状態として記録**すれば、後述のLINE接続で「あの時あとでやる、を押した件です」と再接触できます。

---

### S12 完了カード ─ 記事の終わりを、プロジェクトの一区切りにする

**解く問題**：現状の記事末尾は「無料相談」で終わります。これは**サービス側の都合であって、ユーザーの次の一歩ではありません**。読んだ直後の人が本当に知りたいのは「で、次は何を読めばいい？」です。

**4要素を、この順で置く理由**：

| 順 | 要素 | 意図 |
|---|---|---|
| 1 | ✓ Step 3 を読み終えました | まず承認する。達成の宣言 |
| 2 | ■■■□□□□ 3/7 完了 | 進捗の可視化。残りが見える |
| 3 | 次にやること（1つ・15分） | 実行を渡す。複数出すと選択で止まる |
| 4 | 次に読む（Step 4, 5） | 回遊。★付きで優先度も分かる |

**タスクを1つに絞る理由**：選択肢が増えるほど実行率は下がります（選択のパラドックス）。ここは網羅性ではなく実行率を取る場所です。

**この設計の副作用（正の効果）**：内部リンクが「関連記事」から「順番付きの次」に変わるため、**クロールの意図がGoogleに伝わりやすくなります**。既存の「あわせて読む」は残すので、リンク網は減りません。

---

### S13 目的の取得 ─ 冒頭に置かない

**解く問題**：ユーザーの目的が分かれば、記事の推薦もロードマップ生成も精度が上がります。しかし**取得の置き場所を間違えると、離脱要因にしかなりません**。

**冒頭に置いてはいけない理由**：検索から来た人は「答えを探しに」来ています。答えの前に質問されると、コストだけ払わされて離脱します。

**正しい位置**：**読了後（S12の直後）**。ここなら
- ユーザーは既に価値を受け取っている（返報性が働く）
- 「次に読むものを最適化するため」という**答える理由**が成立する
- 答えなくても記事の価値は毀損しない

**さらに重要な原則：分かっているときは聞かない。**
`?goal=` で来た人、前に選んだ人、LP から流入した人には**このUIを出しません**。既に知っていることを聞くのは、信頼を削るだけです。

---

### S14 CTA ─ 「相談」は目的ではなく手段

**解く問題**：「無料相談」はサービス側の言葉です。ユーザーが欲しいのは相談ではなく**計画**です。

**階層化**：

| 階層 | 文言 | 遷移先 | 対象 |
|---|---|---|---|
| **主** | あなた専用のロードマップを作る（30秒・無料） | `/?occasion={goal}#diagnosis` | 温度が上がった人 |
| 副1 | 次のステップだけ決める | 次の記事へ（S12と同じ） | まだ読みたい人 |
| 副2 | 無料で相談する | `/reserve` | 人に聞きたい人 |

**主CTAが既存機能とつながる点が重要です。** 「90日プラン」は新規開発ではなく、**既に実装済みの `targetDate` 逆算そのもの**です。式の日を入れれば「間に合うもの／間に合わないもの」まで出ます。記事から `?occasion=bigday` を渡せば、Jobが選択済みの状態でプランナーが開きます。

**つまり、記事→プロダクトの接続は新規開発をほぼ必要としません。** 配線するだけです。

## ③ 期待できるユーザー行動

### 行動の変化

| 現状 | 改善後 |
|---|---|
| 記事を読む → 満足 → 離脱 | 記事を読む → 自分の位置を知る → 1つ実行 → 次を読む |
| 「参考になった」で終わる | 「あと4つある」で終わる |
| 相談は温度の高い人だけ | 実行を経た人が相談に来る（＝成約率が上がる） |
| セッション1ページ | セッション2〜3ページ（ロードマップ内回遊） |

### 計測（既存の analytics 層にそのまま乗る）

追加するイベント。すべて `props.goal`（目的）と `props.slug`（記事）を持たせます。

| イベント | 意味 | 見たいこと |
|---|---|---|
| `article_roadmap_view` | ロードマップ・ヘッダーが表示された | 目的の解決率（推定できた割合） |
| `article_task_done` | マイクロ／末尾タスクの「できた」 | **読者→実行者の転換率**（最重要） |
| `article_task_later` | 「あとでやる」 | 再接触の母数 |
| `article_next_click` | 「次に読む」クリック | ロードマップ内の回遊率 |
| `article_goal_set` | 目的の取得UIで回答 | 目的分布の実データ |
| `article_roadmap_cta` | 「ロードマップを作る」クリック | **記事→プランナーの転換率** |

**最重要指標は `article_task_done` です。** ここが動かなければ、他をどう飾っても「読んで終わり」は変わりません。

### 現実的な見積もり

正直に言うと、**この改修だけで相談数が数倍になることはありません**。効くのは順に：

1. **回遊率**（次に読むが明示される）— 最も確実に動く
2. **記事→プランナー転換**（CTAが計画になる）— 動くが、目的の推定精度に依存
3. **相談数**— 母数が増えるので増えるが、率そのものは劇的には変わらない

期待すべきは「相談の**質**が変わること」です。1つでも実行した人の相談は、現在地が具体的なので、その場で構成が決まります。

## ④ 将来接続の設計（LINE・ロードマップ機能へ）

### 段階1（今回の範囲）— localStorage

匿名で読める、を壊さないために、まずブラウザ内に閉じます。

```ts
// key: hr_progress
{
  goal: "bigday",                      // 選ばれた目的
  goalSource: "url" | "picked" | "inferred",
  read:  { "aga-self-check": "2026-07-27T..." },   // 読了
  tasks: { "aga-self-check": "done" | "later" },   // 実践タスクの状態
  targetDate: "2026-10-12",            // その日（プランナーと共有）
}
```

**設計の要点**：`targetDate` を**プランナーと同じ意味で持つ**こと。記事で日付を入れた人が、プランナーで再入力させられるのは体験として最悪です。

### 段階2 — サーバへの持ち上げ（LINE Login）

`site.ts` に LINE の枠（`addFriendUrl` / `liffUrl`）が既にあります。ここに接続します。

```
localStorage の hr_progress
        ↓ LINE Login（LIFF）
  users.progress（サーバ）
        ↓
  ・進捗が端末をまたぐ
  ・「Step 4 がまだです」を送れる
  ・「あとでやる」を押した人に、その件で再接触できる
```

**移行の設計**：ログイン時に localStorage の内容をサーバへ**マージ**します（上書きしない）。既に読んだ分が消えると、それまでの体験が無駄になります。

### 段階3 — ロードマップの自動生成

ここで初めて、記事とプランナーが1つのプロダクトになります。

```
目的（Job）＋ その日（targetDate）＋ 進捗（read / tasks）
        ↓
  composePlan()  ← 既存のエンジン。変更不要
        ↓
  「あなたのロードマップ」
   ・読むべき記事（未読のステップ）
   ・やるべきタスク（未実行のもの）
   ・予約すべき体験（構成モジュール）
   を、1本の時間軸に統合して表示
```

**既存資産で、ほぼ足ります。** `planner.ts` は既に「モジュールの順番・所要・費用・締切からの逆算・間に合わない判定」を持っています。足りないのは**記事とタスクを同じ時間軸に混ぜること**だけです。

### 段階4 — 配信

LINE で「Step 4 の時期です」を送る。ここまで来て初めて、**伴走が仕組みになります**。

## ⑤ SEO / GEO を落とさないためのガードレール

| 項目 | 扱い |
|---|---|
| `<h1>` / `<h2>` | **一切変更しない**。追加要素は `<div>` で、見出しレベルを使わない |
| FAQ | 変更しない。`FAQPage` の構造化データも維持 |
| 内部リンク | 「あわせて読む」は**残す**。「次に読む」は追加であって置換ではない |
| 本文の情報量 | 1文字も削らない。マイクロ・チェックポイントはセクション間に挿入 |
| canonical | 素のURL固定。`?goal=` はインデックス対象にしない |
| 構造化データ | `Article` / `FAQPage` / `BreadcrumbList` は維持。**`HowTo` は足さない**（Googleが一般検索での表示を縮小しており、リスクに見合わない） |
| CLS | ロードマップ・ヘッダーは**高さを固定**して描画する。目的が未解決でもプレースホルダで場所を確保し、後から中身を差し替える |
| 初期HTML | ロードマップ・ヘッダーは**サーバ側でデフォルト目的を描画**し、クライアントで文脈に応じて差し替える。JSなしでも意味が通る状態を保つ |

**GEO（AI引用）への効果**：
「Step 3 / 全7ステップ」「次にやること」という構造は、**AIが手順を再構成しやすい形**です。現在の記事は結論が散在していますが、ロードマップ上の位置と次の行動が明示されると、「◯◯するには何から？」という質問に対して**順序付きで引用されやすくなります**。これは既に `/areas` で入れた「問い→1文回答→要点3つ」と同じ方針の、記事単位への展開です。

## 補足：この設計で「やらない」と決めたこと

- **記事本文の書き換え** — SEO資産を触るリスクに、得られるものが見合いません
- **ゲーミフィケーション（バッジ・ポイント・連続日数）** — 対象が30〜50代の男性で、匿名で読みたい層です。演出が強いほど白けます。進捗バーは「現在地の把握」であって、報酬設計にはしません
- **記事のログイン必須化** — 匿名で読める、はこのサービスの核です。進捗は匿名のまま持てる設計にしています
- **`HowTo` 構造化データの追加** — 表示機会が縮小しており、実装コストに見合いません
