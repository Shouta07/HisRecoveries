## 0. まず、Stripe 側の判断について

**「B2C だから必ず通る」とは考えないこと。**

このサービスは、Stripe の Restricted Businesses のうち
次の区分に近いところにいる。審査で追加の質問が来る前提で用意しておく。

| 区分 | 近さ | なぜ |
|---|---|---|
| Dating services / Matchmaking | **近い** | 恋愛の相談で、成人女性が相談相手として関わる |
| Adult content / services | 遠いが疑われうる | 「女性に相談」という形だけを見ると疑われる。実際には性的サービスは一切提供しない |
| Marketplaces / Multi-party payments | 該当しない | 当社が売主。分配も Connect も使わない |
| Prepaid / Stored value | 該当しない（設計で外した） | 回数券に180日の期限を付け、資金決済法の前払式支払手段から外してある |

Dating に当たると判断された場合、Stripe は
**追加の書類・事業説明・場合により制限**を求めることがある。
その場合も、事実を変えずに、下の説明をそのまま出す。

最終的な判断は Stripe 側にある。こちらでできるのは、
実態と説明を一致させておくことだけ。

## 6. 決済構造（コピペ用）

```
ユーザー
  ↓ Stripe Checkout（当社アカウント・単一）
バイタリティデザイン合同会社
  ↓ 注文・利用権の付与

これだけです。多者間決済はありません。

・Checkout Session はサーバー側で生成します
・金額はサーバー側の定義（単一のソース）から引きます。
  クライアントから金額を受け取る経路を実装していません
・商品IDのみをクライアントから受け取り、サーバーで検証します
・Webhook は署名（HMAC-SHA256）を検証してから処理します
・Idempotency-Key により、二重課金を防いでいます
・同一 session の再送・重複処理でも、利用権は一度しか付与しません
・Stripe Secret Key はサーバー環境変数のみに置き、
  クライアントへ露出しません
```

## 11. 人が用意すること

Stripe に出す前に、人が入れるもの。
コードから確かめられないので、ここには書いていない。

- [ ] `LEGAL_REP_NAME` … 代表者名。**これが無いと決済が開かない**
- [ ] `LEGAL_TEL` … 電話番号。同上
- [ ] 上記2つを Vercel の環境変数に入れる（git には入れない）

この2つが入るまで、`/api/checkout` は 503 を返し、
決済ボタンは押せない（`lib/legal.ts` の `canCharge()`）。
これは意図した動きで、特商法11条の表記が揃う前に
対価を受け取らないようにしてある。
