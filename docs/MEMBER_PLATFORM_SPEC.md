# 会員プラットフォーム構想 — ログイン／血液データ／行動提案／ECマーケットプレイス

> 着想:「HRをログインして使える形に。ID/パスワードでログイン→血液診断データを入れる→それに基づいた行動提案とECマーケットプレイスが広がる」
> 現状: `/member` に **プロトタイプ（デモ）** を実装済み。端末内 `localStorage` のみで完結し、外部送信しない・noindex・「デモ」明示。
> 本ドキュメントは、**本番実装の要件と注意点**を先に固定するためのもの。
> ※ 分析資料。法的助言・医学的助言ではない。本番実装は弁護士・医療専門家レビュー必須。
> 最終更新: 2026-07-11

---

## 0. 結論（3行）

1. **狙いは正しい**：血液データ→行動提案→EC は、HRを「読む」から「使う・続ける」へ引き上げる自然な進化。会員の血液データは、パッケージ／送客／ECすべての起点になる資産。
2. **だが血液データ＝要配慮個人情報**。認証・暗号化・明示同意・利用目的の限定を、実装の"前提"として設計しないと即・地雷。プロトタイプで体験を検証し、本番は正しく作る。
3. **医療行為との線引き**：数値の解釈・診断・治療方針は**医師**が行う。HRの提案は「生活・行動のヒント」に限定し、断定しない。UI全体でこの線を守る。

---

## 1. プロトタイプ（実装済み・`/member`）

- **ログインゲート**：任意のID/PWでデモログイン（本物の認証はしない）。
- **①血液検査データ入力**：testosterone / ferritin / zinc / vitaminD / hba1c / ldl。基準レンジと照らして「低め／高め／範囲内」を表示。
- **②行動のヒント**：範囲外マーカーからルールベースで生活提案。「※数値の意味・対処は医師に」を明示。
- **③ECマーケットプレイス**：モック商品。「あなたへ／すべて」タブ。決済なし、「詳しく見る（デモ）」は無効。
- **安全設計**：`localStorage` のみ・外部送信なし・noindex・冒頭に「プロトタイプ（デモ）／端末内保存／医療行為ではない」バナー。

→ 目的は**体験の検証**。「血液データを入れると提案とECが変わる」の手触りを、リスクゼロで確かめる。

---

## 2. 本番実装の必須要件（プロトタイプでは満たしていない）

| 領域 | 要件 |
|---|---|
| **認証** | 実際のID/PW（ハッシュ化・ソルト）、または SNS/LINE ログイン。多要素認証（MFA）を推奨。セッション管理・ログアウト・パスワード再発行。 |
| **要配慮個人情報の同意** | 血液データは個人情報保護法上の「要配慮個人情報」。取得には**本人の明示的同意**が必須。利用目的（行動提案・商品提案）を明記し、目的外利用・第三者提供の可否を個別同意で。 |
| **暗号化** | 保存時（at rest）・通信時（in transit）ともに暗号化。血液データは特に厳格に。 |
| **アクセス制御** | 本人以外が閲覧できない。運営側の閲覧も最小権限・監査ログ。 |
| **削除権・開示請求** | 会員はいつでもデータ削除・開示請求ができる。退会時のデータ消去フロー。 |
| **医療との線引き** | 提案は「生活・行動のヒント」に限定。診断・治療・医薬品の推奨はしない。医師の関与が必要な提案は、医療機関への中立な案内に留める（`REFERRAL_MODEL_PIVOT.md`の座組）。 |
| **EC/景表法・薬機法** | 商品説明で効果を断定しない。サプリ・化粧品の表現は薬機法遵守。血液データに基づく「あなたに効く」訴求は特に慎重に。 |
| **データの出所** | 血液データは誰が測定したか（提携クリニックの検査／自己申告）で信頼度が違う。提携検査と自己入力を区別して扱う。 |

## 3. データ→提案→ECの設計思想

- **血液データは"起点"であって"結論"ではない**：数値は生活・行動を考えるきっかけ。HRの価値は、数値の羅列ではなく「で、どうすればいい？」への**中立で具体的な伴走**。
- **AIと人の棲み分け**：ルールベース／AIで一次的な行動のヒントを出し、重要な判断・不安の受け止めは人（または提携医）が担う。`MASTER_STRATEGY` の人＋システム思想と一致。
- **ECは"押し売らない"**：数値に紐づく提案は、断定でなく「選択肢」。HRの中立ブランド（モノを売るより、整え方を渡す）を壊さない。アフィリエイト／マーケットプレイス型で、在庫リスクを持たずに広げる。
- **継続の設計**：血液データは時系列で意味を持つ（前回より改善したか）。再検査→記録→変化の可視化が、会員が"続ける"理由になる。

## 3.5 サービスで支える価値＝ゲーミフィケーション（「一連の体験」）

> HRの強みは、単発の施術ではなく **From Complex to Confidence の"一連の体験"を継続で支えること**。会員機能の中心はここ。ただしブランドの声（煽らない・比べない・傷つけない）を壊すゲーミフィケーションは厳禁。

**やらない**：ポイント欲、ランキング（比較＝恥＝ブランドの逆）、罰・赤いストリーク切れ、射幸性。
**やる**：**変化の旅を可視化し、そっと続けられる**設計。

| 仕掛け | 中身 | ブランド適合 |
|---|---|---|
| **章立て（Recovery Journey）** | 気づく→整える→続く→自信。タグラインをそのまま進行アーチに。 | 変化に物語を与える |
| **歩み（steps）** | 続けた小さな一歩の累積。ポイントでなく"歩み"。 | 静かな積み上げ |
| **今日の一歩** | 血液フラグ・悩みから導いた小さな行動をチェック。 | 血液→ヒント→行動が地続き |
| **継続（そっと）** | 連続日数は見せるが、途切れても責めない「また今日から」。 | 傷つけない |
| **節目** | 「3日続いた」等をバッジでなく"節目"として静かに承認。 | 競争でなく承認 |
| **変化の可視化** | 血液・自己評価の時系列。グラフが動くこと自体が報酬。 | 数値でなく変化 |

**物語の本筋は"行くこと"（通院・来店）**：物語（章）は、家のセルフケアではなく **通院（提携クリニックでの検査・施術）と来店（診断・サロン）で前に進む**。行かなければ章は上がらない設計にすることで、①顧客は"楽しみながら次の一歩へ"進め、②HRは送客・パッケージという**収益の起点**に自然に接続する。家での「今日の一歩」は、来訪と来訪をつなぐ道中（歩み）。

クエスト（＝次に行く場所）の例：
1. **相談**（オンライン可）→ 2. **検査**（通院・血液）→ 3. **診断**（来店・印象診断）→ 4. **施術**（来店/通院）→ 5. **メンテ**（定期通院）

**接続がすべて**：記録(血液) → ヒント → 今日の一歩（道中） → 次の物語＝来訪（通院/来店）→ 章が上がる → 変化が見える → 次の来訪・EC。この一本の線が「HRだからこその一連の体験」であり、そのまま収益導線。プロトタイプ `/member` に、章・物語進捗・**次の物語（来訪CTA＋「行ってきた」）**・道のり（クエストマップ）・歩み・節目を実装済み（localStorageのみ）。

**本番での注意**：継続を煽って健康を害する提案をしない／医療判断を要する行動はゲーム化しない／達成の承認は"人の言葉"に近いトーンで（AIの機械的な祝福にしない）。

---

## 4. 段階リリース（安全な順）

1. **Stage 0（今）**：プロトタイプで体験検証。データはローカルのみ。← 実装済み
2. **Stage 1**：認証＋サーバ保存（自己入力データのみ／要配慮個人情報同意＋暗号化）。行動のヒントとECは「一般的情報・選択肢」に限定。
3. **Stage 2**：提携クリニックの検査データ連携（本人同意のもと）。時系列での変化の可視化。
4. **Stage 3**：医師監修の提案・オンライン相談への中立な接続。ここは医療・法務レビューを厳格に。

> 一言: **プロトタイプは「体験の証明」、本番は「信頼の設計」。** 順番を守れば、血液データ起点の会員体験は HR の強い堀になる。急いで health data を本番投入しないこと。
