# Product Brief — Recovery Q&A（モヤモヤ相談室の HR 版）

> 仮称: Recovery Q&A（Check の進化形 / モヤモヤ相談室の His Recoveries 版）。
> 位置づけ: Recovery Check（自己観察 30問 + 編集者の手紙）の**自然な拡張**。
> Phase 1 → 2 の橋渡し。**いまフルで作らない**。最初は手動・軽量で検証。
> 関連: [`BUSINESS_PLAN.md`](./BUSINESS_PLAN.md) §5 / §7.1 / [`RESEARCH_BENCHMARKS.md`](./RESEARCH_BENCHMARKS.md) §1(f) / [`MARKET_THESIS.md`](./MARKET_THESIS.md) §2

---

## 1. 着想の出典 — セイシル / おとなセイシル

TENGA ヘルスケアが運営する [セイシル](https://seicil.com/) は、10代の性のモヤモヤに答える Web メディア。
2019年12月 ローンチ、5年で **年間 600万 PV / 380万訪問 / 1万5千件の相談** に到達。
構成は「性知る？」(キャラクター会話形式の知識記事) + 「モヤモヤ相談室」(匿名で寄せられた
悩みに**複数の専門家が回答**) + 「withセイシル」(コミュニティ)。

**HR への教訓**: タブー領域でも、**匿名相談 × 編集 × 専門家パネル**で巨大な需要が動く
ことの日本での実証。HR の Recovery Check は、これに極めて近い構造で、すでに走っている。
Recovery Q&A はその自然な進化形。

## 2. 一行

Recovery Check の回答と、追加で寄せられる「モヤモヤ」を、編集者と**認証パートナー（専門家枠）**が
答え、匿名化のうえ**公開アーカイブ**として蓄積する。

## 3. なぜ作るのか（堀を太らせる）

- **Check の出力が公開資産になる** — 個別の手紙で終わらせず、匿名化して `/qa` に蓄積すれば、
  SEO/GEO の面（誰かが検索した質問）と一致して**集客と信頼の両輪が回る**。
- **共創の自然な入口** — 認証パートナー（医師・サロンの専門家・心理士など）を「専門家枠」
  として登壇させる場ができる(§7.1 共創、製品ではなく**回答**を共創する)。
- **改善事例ループの加速** — 質問の延長線で「半年後どうなった?」を追跡しやすい構造。
- **静かなネットワーク効果** — 質問が増えるほど、似た悩みの男性が辿り着き、また質問する。
  セイシルが 5年で 1.5万件まで積んだのと同じフライホイール。

## 4. 構成（最小）

1. **入口**: Recovery Check 内 or 専用フォーム `/ask`。匿名（必須）+ 領域選択 + モヤモヤ本文。
2. **回答**: 編集者の手紙 + （必要に応じ）専門家パネル 1〜3名のコメント。診断はしない。
3. **公開アーカイブ**: `/qa/[id]` に匿名で公開（投稿者の同意を取る）。Article + FAQPage 構造化データ。
4. **クロスリンク**: 各 territory / feeling 末尾に「関連するモヤモヤ」を表示。
5. **季節の問い**: Recoveries Letter で「次の半歩」のヒントとして再配信。

## 5. ブランド原則（守らないとセイシルの真似になる）

- HR の register は**大人男性・静か・Aesop寄り**。キャラクター・ポップな絵は使わない。
- **「相談に答える」より「観察を一緒に置く」**。診断・断定はしない。一人称・過去形を保つ。
- 専門家の回答も**売り込みにしない**。HR の編集が事前に文体を揃える(認証の中立性を守る)。
- **不安を煽らない / 急がせない**。

## 6. パートナー（専門家枠）の規律

- 認証パートナーのみが登壇可（§7 の 5原則を満たす者）。
- **回答は HR 編集が必ず査読**。営業的な誘導は不可。
- **回答=広告ではない**。回答内のリンクは原則禁止。読者の選択を残す。
- **HR とパートナーの利益相反は事前開示**（共創の規律 §7.1）。

## 7. 規制・倫理ゲート（必須）

- **薬機法 / 医療広告ガイドライン**: 医療効果の断定・受診勧奨を回答に含めない。
  「個別の判断は医療機関へ」を回答末尾の定型として固定。
- **個情法**: 匿名化（投稿者同意 + 識別子の除去 + 文章中の固有名詞のマスク）。
- **同意**: 投稿時に「公開アーカイブへの匿名掲載」へ目的別の opt-in を取る
  ([`TECH_SPEC.md`](./TECH_SPEC.md) の consent モデルに準拠)。

## 8. 段階展開（フェーズ）

| フェーズ | 内容 | コスト |
|---|---|---|
| **Step 0（今）** | Check の回答に、編集者の手紙で対応。`/qa` はまだ作らない | 0 |
| **Step 1** | 手紙のうち**特に共有価値の高い問い**を、本人同意のもとで匿名化し `/qa/[id]` に1件ずつ手動公開 | 小 |
| **Step 2** | 専用フォーム `/ask` を実装。専門家枠 1〜2名を試験運用（認証パートナーから） | 中 |
| **Step 3** | territory/feeling/Letter とのクロスリンク自動化。改善事例ループ統合 | 中 |
| **Step 4** | コミュニティ機能（with セイシル相当）を、HR の静けさを保つ形で検討 | 大 |

**今やる**: Step 0 → 1 の足場。新規ルートやスキーマは要らない（既存の `concerns` 構造を流用可）。

## 9. KPI（Phase 0〜1）

- 月次の Q&A 公開件数 / 1件あたりの平均流入 / SEO/GEO のロングテール拾得 /
  Q&A 経由の Check 起動率 / 専門家パネルの回答品質スコア（編集者による評価）。

## 10. 未決事項

- 入口を `/check/start` 内に混ぜるか、独立 `/ask` にするか。
- 専門家パネルの最初の 1名をいつ・どう選ぶか（HR の認証第1号と兼ねる選択肢）。
- アーカイブの URL 設計（`/qa/[id]` vs `/feelings/[slug]/qa/[id]` 等）。
- 改善事例（Stories）と Q&A の関係（同じスキーマで束ねるか、別に保つか）。

HR が同じ型で「男性の自意識」を扱った場合の市場性を、強く後押しする。*
