# 決済の設計とセキュリティ（Stripe）

His Recoveries の決済は **Stripe Checkout（ホスト型）** で行う。
この文書は「なぜその形にしたか」と「何を守っているか」を残すためのもの。

---

## 1. 何を売るか、どう払われるか

商品は1本だけ。

| | |
|---|---|
| 商品 | 第一印象改善プラン（30日） |
| 価格 | ¥49,800 税込（先着10名） / ¥66,000 税込（11名以降） |
| 実施 | 東京都内・土日のみ・1日 |
| 決済 | クレジットカード（Stripe Checkout） |
| 返金 | お支払い後のキャンセル・返金なし（日程変更は1週間前まで） |

金額は `src/lib/pricing.ts` の1箇所だけに書く。
サイトの表示・Stripe の請求・管理画面は、すべてここを見る。

---

## 2. 公開サイトに「今すぐ購入」ボタンを置かない

これは技術ではなく商品設計の判断だが、結果としてセキュリティ上も効いている。

**理由（商品側）**
サイトには「合わないと思えば、その場でそうお伝えします」「迷いが残っているうちは、
お勧めしません」と書いてある。誰でも押せる購入ボタンは、この約束と矛盾する。
返金なしの商品で、納得していない人に決済させてはいけない。

**理由（安全側）**
決済セッションを作れる公開エンドポイントが存在しないので、
いたずらに大量のセッションを作られる余地がない。

**実際の流れ**

```
無料相談（メールフォーム）
  └─ 合うかどうかを先に確認
       └─ 実施日を決める
            └─ 管理画面 /admin/checkout でお支払いリンクを発行
                 └─ メールでURLを送る
                      └─ 顧客がStripeの画面でカード入力
                           └─ Webhook で入金確定・枠を1つ消費
                                └─ 伴走用LINEをご案内
```

## 3. 守っていること

### 3.1 カード情報がこちらを通らない

カード番号の入力は `checkout.stripe.com` 上で行われる。
自前のフォームでカード番号を受け取らないので、PCI DSS の適用範囲は **SAQ-A** に収まる。
アプリのDBにカード情報を保存する箇所は存在しない。

### 3.2 金額はサーバーが決める

`POST /api/admin/checkout` が受け取るのは
**tier（founder / standard）・宛先メール・呼び名・実施日・運用メモ** だけ。
**金額は受け取らない。** サーバーが `STRIPE_PRICE_*` か `src/lib/pricing.ts` から引く。

→ リクエストを改竄しても金額は変えられない。

### 3.3 決済リンクを作れるのは管理画面だけ

`src/middleware.ts` の matcher が `/api/admin/:path*` を含むので、
このAPIは Basic 認証（`ADMIN_PASSWORD`）を通らないと到達しない。
公開されている決済系エンドポイントは Webhook のみ。

### 3.4 Webhook の署名検証

`/api/stripe/webhook` は認証なしで叩けるので、ここが唯一の攻撃面になる。

- `stripe.webhooks.constructEvent()` で署名を検証する
- **検証は生のボディで行う**。`req.json()` を先に呼ぶと検証が通らなくなるため、
  必ず `await req.text()` を使う（`runtime = "nodejs"`）
- タイムスタンプの許容ずれは **5分**。それより古いリクエストは弾く
  → 過去の正規リクエストを録って投げ直す**リプレイ攻撃**を防ぐ
- 署名が通らなければ **400 を返して一切書き込まない**

### 3.5 署名が通ったあとも、内容を自分で確かめる

署名は「Stripe から来た」ことしか証明しない。ハンドラ側で追加確認する。

- `payment_status === "paid"` か
- `currency === "jpy"` か
- その `session_id` を**自分が発行したか**（`orders` に存在するか）
  → 知らないセッションは記録だけ残して処理しない

### 3.6 冪等（同じ通知が二度来ても壊れない）

Stripe は配信を保証するため、同じイベントを再送することがある。

- **発行時**：`idempotencyKey`（tier + email + 実施日）を Stripe に渡す。
  二重送信しても Checkout Session は1つしか作られない
- **入金時**：`markOrderPaid` の更新条件に `status=neq.paid` が入っている。
  すでに `paid` の行は二度目の更新を受けない = 枠を二重に消費しない
- `stripe_session_id` に UNIQUE 制約（`supabase/schema.sql`）

### 3.7 ハンドラが落ちたら 500 を返す（握りつぶさない）

DB書き込みに失敗したときに 200 を返すと、Stripe は「届いた」と判断して再送しない。
入金が記録から消える。なので失敗時は **500 を返して Stripe に再送させる**。

### 3.8 秘密鍵の露出防止

- `STRIPE_SECRET_KEY` / `STRIPE_WEBHOOK_SECRET` に `NEXT_PUBLIC_` を**付けない**
  （付けた瞬間クライアントのJSに埋め込まれる）
- `src/lib/stripe.ts` にガードを入れてある。`NEXT_PUBLIC_*` の値が
  `sk_` / `rk_` / `whsec_` で始まっていたら **例外を投げて起動させない**
- `src/lib/stripe.ts` は API ルートとサーバーコンポーネントからのみ import する

### 3.9 先着10名をサーバーで止める

コピーに「先着10名」と書くだけにしない。`orders` テーブルを数えて発行を止める。

- 発行時は `issued + paid` を数える（二重発行の防止）
- 上限に達していたら **409 を返して発行しない**
- 期限切れ（`checkout.session.expired`）は `expired` に落として枠を返す

### 3.10 注文テーブルは anon から触れない

`orders` は RLS を有効にし、**ポリシーを1つも作らない**。
anon key では読めない・書けない。service key を持つサーバーだけが操作する。

### 3.11 成功ページはURLを信用しない

`/checkout/success?session_id=...` は、その値をそのまま表示しない。
`stripe.checkout.sessions.retrieve()` で問い合わせ、`payment_status === "paid"`
を確認してから完了画面を出す。形式（`cs_...`）も正規表現で確かめる。

### 3.12 返金・チャージバックは自動処理しない

`charge.refunded` / `charge.dispute.created` はログに残すだけで、
状態は自動で変えない。人が確認して判断する。

## 4. セットアップ手順

### 4.1 Supabase

`supabase/schema.sql` の `orders` 部分を SQL Editor で実行する。

### 4.2 Stripe ダッシュボード

1. **APIキー**（開発者 → APIキー）
   シークレットキーをコピー → `STRIPE_SECRET_KEY`
   まずは `sk_test_` で通してから `sk_live_` に差し替える。

2. **Webhook**（開発者 → Webhook → エンドポイントを追加）
   - URL: `https://hisrecoveries.com/api/stripe/webhook`
   - 送信するイベント:
     - `checkout.session.completed`
     - `checkout.session.expired`
     - `charge.refunded`
     - `charge.dispute.created`
   - 署名シークレット（`whsec_...`）をコピー → `STRIPE_WEBHOOK_SECRET`

3. **商品と価格**（任意だが本番では推奨）
   商品「第一印象改善プラン（30日）」を作り、価格を2つ作る。
   - ¥49,800（税込・一括）→ `STRIPE_PRICE_FOUNDER`
   - ¥66,000（税込・一括）→ `STRIPE_PRICE_STANDARD`
   未設定でも動く（`pricing.ts` の金額で都度組む）が、
   Price を作っておくと金額の変更履歴が Stripe 側に残る。

4. **顧客への領収書**（設定 → 顧客のメール）
   「支払いが成功したときに領収書を送信」を ON にする。
   こちらでPDFを発行・保管しない。

### 4.3 Vercel

環境変数を Production / Preview に設定する。
`NEXT_PUBLIC_` を**付けない**こと。

### 4.4 ローカルでの動作確認

```bash
# 1. Stripe CLI で Webhook をローカルに転送
stripe listen --forward-to localhost:3000/api/stripe/webhook
# 表示された whsec_... を .env.local の STRIPE_WEBHOOK_SECRET に入れる

# 2. /admin/checkout でテストモードのリンクを発行

# 3. テストカードで支払う
#    4242 4242 4242 4242 / 任意の将来日付 / 任意のCVC
```

## 5. 消費者保護まわりの確認事項

技術ではないが、決済を通す前に必ず見る。

- **特定商取引法**：通信販売に該当するため、事業者名・所在地・連絡先・
  価格・支払方法・提供時期・**返品特約**の表示が必要。
  返金不可であることは、注文の前に明確に示さなければならない。
  → Checkout の `consent_collection.terms_of_service` で同意を取っている。
  加えてサイト側（価格・信頼・はじめかた・FAQ）にも書いてある。

- **特定継続的役務提供**：エステティックは
  「1か月を超え」**かつ**「5万円を超える」で該当する。
  現在の 30日 × ¥49,800 はどちらの条件も超えていない。
  ただし **¥66,000 に上げると金額の余裕がなくなり、期間の条件だけが壁になる。**
  価格改定の前に、必ず弁護士に確認する。

- **景品表示法（二重価格表示）**：
  ¥66,000 を「通常価格」として取り消し線つきで見せない。
  これは将来の価格であって、過去に販売した実績のある価格ではない。

## 6. 今後、公開の購入導線を作る場合

もし self-serve に切り替えるなら、以下を足す必要がある。

- 公開の `POST /api/checkout` を作る（管理APIとはハンドラを分ける）
- **レート制限**（IPあたり / 分あたり）。管理APIは認証で守られているが、
  公開エンドポイントには必須
- **Bot対策**（Turnstile / hCaptcha）
- 先着枠のカウントを、発行時ではなく**予約（hold）とTTL**で管理する
- 特商法表記ページの新設（現在は各所に分散して書いている）

いまはこれらが不要な形にしてある。
