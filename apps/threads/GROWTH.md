# タシカメ Threads — 有料100人までの設計

目的は投稿を増やすことではない。**有料の人を100人**にすること。
この文書は、そのために何を作り、何を測り、何をやめるかを決める。

対象は `@koikame.jp`。実装は `apps/threads/`、計測は `src/lib/analytics.ts` と
`events` テーブル。書き方の規則は `READ_DESIGN.md`（この文書は「何を回すか」を扱い、
「どう書くか」は触らない）。

---

## 0. いまの地点

| | 状態 |
|---|---|
| 投稿 | 旧事業の153件を削除中（100件完了・残り53件）。**実質ゼロから** |
| 実績データ | `history.json` は空。**自社の数字が1つも無い** |
| 生成 | 5場面の連投。動く（`writer.py` → `_build_thread_prompt`） |
| 承認ゲート | 有効。生成は `approvals.json` に積まれ、承認したものだけ出る |
| 投稿枠 | 生成 09:00 / 21:00、投稿 10:30・13:30・16:30・19:30・22:30 |
| 計測 | `site_landed → plan_viewed → checkout_started → purchase_paid` まで実装済み |
| 送客先 | `/ask?plan=review&c={slug}` ＝ **¥10,800 のパス** |

**最初の仕事は、売ることではなく数字を作ること。** 自社の表示数・クリック率・
購入率が1つも無い状態で配分を決めても、それは勘でしかない。

## 1. ゴールの分解

### 「100人」は売上目標ではない

売る商品は3つ（`src/lib/ask/plans.ts`）。

| id | 名前 | 金額 | 役 |
|---|---|---|---|
| `first` | はじめの1件 | ¥980 | 入口。1人に読んでもらう |
| `review1` | 3人に見せる | ¥2,380 | 本来の形 |
| `review` | 3人 × 5回 | ¥10,800 | 続ける人の持ち方 |

100人を ¥980 だけで取ると売上 ¥98,000、粗利率は 0.39（`marginFloor`）で
手元に残るのは4万円弱。**100人は通過点であって、ゴールの形ではない。**

目標を2本立てにする。

- **人数**: 有料100人（＝ブランドが成立したことの証明）
- **質**: そのうち15人以上がパス（¥10,800）に上がる（＝事業が回ることの証明）

人数だけを追うと ¥980 の配布になり、質だけを追うと母数が集まらない。

### ファネルの式

```
投稿の表示数
  × リンククリック率        ← Threadsはリンク付き投稿の露出を落とす
  = 着地（site_landed）
  × 購入率                   ← 相談を書いて画像を上げる手間がある
  = purchase_paid
```

自社の値が出るまでの**仮置き**（一般的なレンジの下寄り・中央・上寄り）:

| | 悲観 | 中央 | 楽観 |
|---|---|---|---|
| 1連投あたりの表示 | 800 | 2,000 | 5,000 |
| 表示 → クリック | 0.3% | 0.5% | 1.0% |
| 着地 → 購入（¥980） | 1.0% | 2.5% | 5.0% |

中央値で100人に必要な表示数:

```
100 ÷ 0.025 = 4,000 着地
4,000 ÷ 0.005 = 800,000 表示
1日2連投 × 2,000 = 4,000/日  →  200日
```

**約6〜7ヶ月。しかもこれは「表示が落ちない」前提。** 実際には新規アカウントの
初速は低く、リンク付き投稿はさらに落ちる。

### ここから出る結論

> **リンク経由の送客だけでは、現実的な期間で100人に届かない。**

だから設計の中心は「投稿を増やす」ではなく、
**リンクに依存しない導線を1本持つこと**になる。

## 2. 中心にするもの — 公開タシカメ

**商品の出力そのものが、Threadsでいちばん強いコンテンツ。**

タシカメが返すのは「実在の女性3人が、実際にどう読んだか」。
これを公開でやると、3つが同時に起きる。

1. **リプライが増える** — 2026年のアルゴリズムで最重要の指標（`READ_DESIGN.md` §0）
2. **証明になる** — 「実在の女性が読む」を信じてもらう唯一の方法は、見せること
3. **リンクが要らない** — 露出が落ちない

生成投稿（5場面の連投）は、これを支える周辺に置く。逆ではない。

### 型

```
月曜  募集投稿（リンク無し）
      「今週1件だけ、公開で確カメます。
        送る前で止まっている文面を、リプに貼ってください」

火曜  1件選ぶ → 本人にDMで公開の許可を取る → 匿名化

木曜  結果投稿（連投・リンク無し）
      1投目  元の文面（匿名化済み）
      2投目  3人がどう読んだか（判定と理由）
      3投目  割れたところ / 共通して出たところ
      4投目  「これは公開ぶん。自分のを確かめたい人はプロフィールから」
```

### 規則（破ると事故になる）

- **許可を取るまで出さない。** リプに貼られた＝公開の同意、にはしない
- **匿名化**: 名前・地名・勤務先・年齢の実数・固有名詞を落とす。画像は出さない
- **無料で配るのは公開の1件だけ。** 個別に無料で返さない
  （返した瞬間に ¥980 を買う理由が消える）
- **返ってくるのは「読んだ女性がどう受け取ったか」。** 相手の気持ちの判定はしない
  （`persona.json` の `business_context.boundary`）
- **公開ぶんも回答者に ¥500 払う。** 宣伝だからと無償にしない

### 週あたりの構成

| | 内容 | リンク |
|---|---|---|
| 月 | 公開タシカメ・募集 | 無し |
| 火〜水 | 生成の連投（5場面から2本） | 最終投稿に1本 |
| 木 | 公開タシカメ・結果 | 無し |
| 金〜日 | 生成の連投（2本）＋ 問いかけ1本 | 連投のみ |

リンク付きは**週4本まで**。それ以上出すと、アカウント全体の露出が落ちる。

## 3. いますぐ直すこと

### 3.1 送客先が高すぎる

`hypotheses.json` の `link_config.base_urls.apply`:

```
https://hisrecoveries.com/ask?plan=review&...   ← ¥10,800
```

Threadsから来た人は、サービスを3分前に知ったばかりで、
「実在の女性が読む」を**まだ信じていない**。そこに ¥10,800 を出すのは早い。

```
plan=review  →  plan=first    （¥980・1人・`trial: true`）
```

パスは、1件届いたあとに上げる。順序が逆だと、信じる前に金額で落ちる。

> 補足: `review1`（¥2,380・3人）を入口にする案もある。タシカメの価値は
> 「割れたことが分かる」ことなので、3人のほうが商品として正しい。
> ただし冷たい流入の入口としては ¥980 が通りやすい。
> **Phase 2 で A/B を回して決める**（どちらが結局パスまで上がるか）。

### 3.2 どの投稿が売ったか分からない

いまのUTMは `utm_campaign={slug}` のみ。場面（message/photo/…）までしか分からず、
**どの投稿が効いたかが分からない**。

```
&utm_content={post_id}
```

を足す。これが無いと §5 の学習ループが回らない。
投稿を増やしても、何が効いたか分からないまま増えるだけになる。

### 3.3 CTAが4投目にある

連投の最終投稿にだけリンクを置いている（露出を守るためで、これ自体は正しい）。
ただし4投目まで読む人は一部なので、**プロフィールのリンクが第2の入口**になる。

- プロフィールのリンクを `plan=first` ＋ `utm_source=threads&utm_medium=profile` に
- 公開タシカメの結果投稿は、プロフィールへ誘導する（投稿内にリンクを置かない）

## 4. 承認の負荷を下げる

承認ゲート（`immediate_posting_forbidden`）は外さない。
生成物をそのまま出すと、ブランドの線（§2の規則）を越えたものが出る。

ただし **1日5枠ぶんを毎日承認するのは続かない。**

```
日曜に1回、翌週ぶん（4〜6本）をまとめて承認する
```

`approvals.json` はキューなので、承認済みが溜まっていれば
`post-approved` が枠の時間に順に出す。運用は週1回15分で足りる。

---

## 5. 学習ループ（これが「オートメーション」の本体）

投稿の自動化はすでに動いている。**足りないのは、結果が次の投稿に返る経路。**

```
日次  collect        Threads API → 表示数・リプライ数 → history.json
日次  attribute      events テーブル（utm_content）→ 投稿ID別の着地・購入
週次  evaluate       場面 × フックごとに「表示・リプライ・着地・購入」を集計
                     → experiments.json の配分を更新
                     → 負けている場面は status を paused に
```

### 判定の順序

リプライ数だけで決めない。リプライが多くても買われない場面がある。

1. **表示数** — 読まれているか
2. **リプライ率** — 会話になっているか（＝次も表示されるか）
3. **着地率** — リンクが押されているか
4. **購入率** — 金を払う人の話だったか

4が最後まで見えるのは、母数が溜まってから（1場面あたり10本・`min_posts_to_evaluate`）。
それまでは1と2で回し、**3と4で止める判断はしない**。

### 既にある部品

- `collector.py` — 表示数の取得
- `experiments.json` — 場面別の投稿数とフェーズ
- `events` テーブル — UTM付きの着地と購入

**足りないのは、この3つを突き合わせる週次の集計。** これを作る（§9 Phase 2）。

## 6. 返信は人がやる

> 投稿直後の反応でおすすめ露出が決まる。**最初の1時間の返信には必ず返信する**
> （`READ_DESIGN.md` §0）

ここは自動化しない。理由は2つ。

- **規約** — 自動返信は本文の自動投稿とは別の線。アカウントを失う
- **ブランド** — 「実在の人が読む」を売っている。返信が機械だと、商品の嘘になる

1日15分。投稿の直後15分と、夜に10分。これが**表示数の最大の変数**で、
投稿を1本増やすより効く。

## 7. 供給側の上限（需要を増やす前に確認する）

有料100人が実現すると、必要な回答は:

| 想定 | 回答数 | 回答者への支払い |
|---|---|---|
| 85人が ¥980（1人）＋ 15人がパス（3人×5回） | 85 + 225 = **310件** | ¥155,000 |

**回答者が足りないと、売れた瞬間に破綻する。** 届かない約束を売ったことになる。

- 1件あたりの納期（SLAは何時間か）
- 同時に捌ける件数
- 回答者の稼働人数と、1人あたりの週の上限

**Phase 1 に進む前に、この3つを数字で押さえる。**
ここが詰まっているなら、Threadsの設計をどう直しても意味がない。

## 8. 週に見る数字（6つだけ）

多く見ると、どれも動かせなくなる。

| 数字 | どこから | 何を決めるか |
|---|---|---|
| 1連投あたりの表示数 | `history.json` | 書き方が効いているか |
| リプライ率 | `history.json` | 次も表示されるか |
| プロフィール経由の着地 | `events` (`utm_medium=profile`) | 公開タシカメが効いているか |
| 投稿経由の着地 | `events` (`utm_medium=social`) | リンク導線が効いているか |
| 着地 → 購入 | `site_landed` → `purchase_paid` | サイト側の問題か、集客の問題か |
| パス率 | `purchase_paid` の `plan` 分布 | 事業として回るか |

フォロワー数は見ない。表示数と連動しないうえ、**買う人の数とは関係がない**。

## 9. 段階

### Phase 0 — 土台（1〜2週）

売らない。数字を作る。

- [ ] 残り53件の削除を完了する
- [ ] 送客先を `plan=first` に変更（§3.1）
- [ ] `utm_content={post_id}` を追加（§3.2）
- [ ] プロフィールのリンクを設定（§3.3）
- [ ] 回答者の供給を数字で確認（§7）
- [ ] 1日1連投で2週間。**リンク無しで**、表示数の地力を測る

**出口**: 1連投あたりの表示数の中央値が分かっている。

### Phase 1 — 公開タシカメ（3〜6週）

- [ ] 公開タシカメを週1本で開始（§2）
- [ ] 生成の連投を1日1〜2本、リンクは週4本まで
- [ ] 返信を毎日15分（§6）

**出口**: 表示数が Phase 0 の2倍。リプライが毎回つく。最初の購入が出る。

**やめる条件**: 6週で公開タシカメに1件も応募が来ない
→ 募集の文面ではなく、**アカウントがまだ信じられていない**。Phase 0 に戻る。

### Phase 2 — 学習ループ（6〜12週）

- [ ] 週次の集計を実装（§5）
- [ ] 場面別に配分を更新。負けている場面を止める
- [ ] 入口の A/B（`first` ¥980 対 `review1` ¥2,380）を回す（§3.1）

**出口**: 「どの場面のどのフックが買われるか」が数字で言える。

### Phase 3 — 増やす（12週〜）

勝ち筋が分かってから初めて量を増やす。
それまでは**投稿を増やさない**。効かないものを増やしても、効かない量が増えるだけ。

## 10. この設計が前提にしていること

外れたら設計ごと見直す。

1. **Threadsのリンク露出は落ちる** — 落ちないなら、リンク導線をもっと使える
2. **公開タシカメに応募が来る** — 来ないなら、信用の作り方を別で考える
3. **¥980 なら冷たい流入でも買われる** — 買われないなら、価格ではなく
   「実在の女性が読む」が伝わっていない
4. **回答者の供給が需要に追いつく** — 追いつかないなら、集客より先にそちら

## 11. 何を自動化し、何をしないか

| | 自動 | 理由 |
|---|---|---|
| 生成 | ◯ | 型が決まっている |
| 投稿 | ◯ | 枠が決まっている |
| 数値の収集 | ◯ | APIで取れる |
| 配分の更新 | ◯（週次） | 数字で決まる |
| **承認** | ✕ | ブランドの線は人が引く |
| **返信** | ✕ | 規約とブランドの両方 |
| **公開タシカメの選定・許可取り** | ✕ | 人の文面を扱う。事故が取り返せない |

**自動化の目的は、人の時間を「返信」と「公開タシカメ」に寄せること。**
投稿を人手ゼロで回すことではない。
