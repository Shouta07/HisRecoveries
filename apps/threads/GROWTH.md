# 恋亀 Threads 運用設計

Threads を集客媒体ではなく、**恋亀というキャラクターを育てる場**として回す。

```
恋亀を知る → 共感する → コメントする → 好きになる
→「自分の話も聞いてほしい」→ サイト → 恋亀と話す → 続ける → 課金
```

この文書は「何を回すか・何を測るか・何をやめるか」。
**書き方**は `READ_DESIGN.md`、**恋亀の人格**は `src/lib/koi/prompt.ts` が持つ。

---

## 0. 先に、詰まっているところ

この導線は、いまのままでは**最後まで通らない**。3つ止まっている。

### 0.1 恋亀と話せない

`src/lib/koi/gate.ts`:

```ts
const KEY = process.env.REALTIME_API_KEY;
export const koiEnabled = Boolean(KEY);
```

鍵が入っていないので `koiEnabled = false`。トップの2行目は
**「迷ったら、実在する女性に確カメる。」** に落ちている（`SUB_NOW`）。

> 「恋亀に話すだけ。」と1画面目に書いたとき、
> 押しても話せないなら、それは嘘になる。 — `gate.ts`

鍵が入るまで、投稿 C・D は「恋亀と話す」ではなく
**「実在する女性に確カメる」**を書く（§4.3）。

### 0.2 住所 — 決まった

**`https://tashikame.app/`**（2026-10-03）。差し替えは済んでいる。

- `src/lib/site.ts` の既定値（canonical・OGP・sitemap・feed・Checkout が全部ここを読む）

- Search Console のリンク、Stripe 申請の URL 一覧

**残っているのはコードの外**（`docs/DOMAIN_MIGRATION.md` の「手順」）。
Vercel にドメインを足す・DNS を向ける・旧住所から301・Search Console の

> 払ったあとに行き先が無い。

> ハンドルは `@koikame.jp` のままなので、**ハンドルと住所は一致しない**。

### 0.3 課金の先が「確カメる」のまま


**この3段は、そのまま §3 の導線になる。**

## 1. 恋亀は1人

Threads の恋亀と、アプリの恋亀は**同じ人格**でなければならない。

違うと、いちばん高い代償を払う場所で壊れる。
Threads で好きになった亀と、話してみた亀が別人だと、
**「自分の話も聞いてほしい」で来た人が、その場で離れる。**

### 正は `src/lib/koi/prompt.ts`

人格はそこにあり、Threads 側は**写すだけ**。
Threads 用に人格を書き直さない（`writer.py` に人格を直書きして
`persona.json` が効かなくなった失敗を、もう一度やることになる）。

| | アプリの恋亀 | Threads の恋亀 |
|---|---|---|
| 口調 | 関西寄り。「〜やん」「〜やな」 | 同じ |
| 長さ | 1回2文まで | **投稿は4〜8行まで**（読み物なので少し長い） |
| 質問 | 1回に1つ | 同じ。**最後は必ず問いで閉じる** |
| 敬語 | 使わない | 同じ |
| 説教 | しない | 同じ |
| 絵文字 | **使わない**（画面が亀を出す） | **🐢を1つ使う**（下記） |

### 🐢 だけは変える

アプリでは画面に亀がいるので、恋亀は絵文字を使わない。
**Threads には画面が無い。** 🐢 が、恋亀がそこにいることを示す唯一の印になる。

- 1投稿に **1個だけ**。多いと「キャラ運用」に見えて、人格に見えなくなる
- 置くのは**文末**。文中に散らさない
- `persona.json` の `tone.emoji_usage` は `0〜2個` なので、規則としては既に通る

### 越えてはいけない2本

`prompt.ts` の `NEVER` は人格ではなく**約束**（利用規約 第12条）。
Threads でも同じだけ効く。

**1. 「脈あり」「脈なし」「本命」を使わない**

ブリーフ 17 のテーマ一覧に「脈ありに見える行動」「脈ありに見えるけど確信がない」がある。
**この言い方は使えない。** 相手の気持ちを当てる言い方だから。

ただし**扱いたい心理は正しい**。言い換えれば全部書ける。

| 書けない | 書ける |
|---|---|
| 脈ありに見える行動 | 「脈ありかどうか」より、**分からない時間のほうがしんどい** |
| 脈なしかも | 嫌われたんじゃなくて、**嫌われてるか分からない** |
| 本命じゃないのかな | 自分が何番目かを数えてしまう時間 |

ブリーフ【型2】の

> 「嫌われた」じゃなくて「嫌われてるか分からない」状態な気がする🐢

は、**この言い換えが既にできている。型2 を基準にする。**

**2. 「女性は」「男性は」と代弁しない**

ブリーフ B と【型3】は男女差が軸。これ自体は**問題ない**。
境目は、恋亀が**聞くか、代弁するか**。

| 書けない | 書ける |
|---|---|
| 女性はこう受け取ります | 男性に聞きたい。これどう受け取る？🐢 |
| 男はこう思うもの | やっぱこれ割れるな🐢 |
| 女心はこう | そう感じる人もおるんやな |

**「割れた」と言うのは、代弁の逆。** 一つにまとまらなかったという事実を言っている。
タシカメの思想そのものなので、ここは強く出してよい。

> 恋亀は、答えを持っている亀ではない。**問いを持っている亀。**

## 2. プロフィール

ブリーフ7の案を、実態に合わせて1行だけ直す。

```
恋愛だけ妙に考える亀🐢
マチアプで出会った後の
LINE・デート・相手の温度感について喋ってます。
迷ったら、人にも確カメる。
↓
tashikame.app
```

ハンドル（`@koikame.jp`）と住所（`tashikame.app`）が違うので、
**「確カメる」の一行が、2つをつなぐ唯一の手がかり**になる。ここは削らない。

- 「人にも確カメる」は、いま売っているものと一致している（§0.3）。そのまま使える
- 企業名は出さない。**法務情報はサイト側**（特商法・規約）で正確に出す
- リンクは `?utm_source=threads&utm_medium=profile` を付ける。**これが主導線**（§5）

## 3. 導線を、実装の名前に落とす

ブリーフの導線を、`src/lib/analytics.ts` のイベントに対応させる。
**対応するイベントが無い段を、KPI にはできない。**

| 段 | いまの計測 | 状態 |
|---|---|---|
| Threads で知る | Threads API の表示数 | ◯ `collector.py` |
| コメントする | Threads API の返信数 | ◯ |
| プロフィールを見る | **Threads の Insights** | △ 取得していない |
| サイトを開く | `site_landed` (`utm_medium=profile`) | ◯ |
| 恋亀と話し始める | — | **✕ 無い** |
| 初回を話し終える | — | **✕ 無い** |
| 2回目に戻ってくる | — | **✕ 無い** |
| 課金 | `purchase_paid` | ◯ |

### 足すイベント

`CONVERSION_EVENTS` に4つ足す（許可リストは `analytics.ts` が唯一の出どころ）。

```ts
"koi_started",    // 恋亀と話し始めた（props: from, nth）
"koi_completed",  // 最後まで話した（props: minutes, nth）
"koi_returned",   // 2回目以降に戻ってきた（props: nth, days_since）
"koi_to_ask",     // 恋亀との話から確カメるへ進んだ（props: category）
```

`koi_to_ask` が、**恋亀（無料）と確カメる（有料）のつなぎ目**。
ここが動かないなら、恋亀をいくら育てても売上にならない。

## 4. 投稿の構成

ブリーフ4の比率を採用する。1日の本数は §6。

### 4.1 比率

| | 種類 | 比率 | 目的 | リンク |
|---|---|---|---|---|
| A | 共感・あるある | 40% | 共感・保存・返信 | 無し |
| B | 男女で割れる問い | 30% | **コメントを起こす** | 無し |
| C | 恋亀コンテンツ | 20% | プロダクト理解 | 無し |
| D | 告知 | 10% | 送客 | **有り** |

**リンクを貼るのは D だけ。** Threads はリンク付き投稿の露出を落とす（`READ_DESIGN.md` §0）。
A・B・C はリンク無しで回し、送客はプロフィールが担う。

### 4.1.1 恋亀が、投稿の中にいること

**🐢を外して読んでみて、誰が書いても同じなら、それは恋亀ではない。**

```
返信遅いけど、会うとめっちゃ楽しそう。
これ一番むずくない？          ← 誰でも書ける
```
```
返信は3日に1回。
でも会ったら4時間しゃべってる。

どっちがほんまなん、ていう話やけど
たぶん両方ほんま。

これが一番むずいやつやな🐢    ← 恋亀がいる
```

基準は `src/lib/koi/demo.ts`。**「次回予告きてるやん」「惜しい（笑）」**の水準。
説明口調になったら、それは恋亀ではない。

### 4.1.2 恋亀は意見を持つ。外れていてよい

**「断定しない」と「意見を持たない」は別のこと。**

```
恋亀はこれ男女で割れそうだと思ってる🐢   ← 意見の不在。誰も反論できない
```

誰も反論できない投稿には、返信が来ない。
返信を生むのは**訂正したくなること**。

```
恋亀は②に見えた。
「〜」が効きすぎてる気がする。

①に見えた人、理由おしえて🐢
```

見立てを出し、理由を1行つけ、違う人に聞く。外れているから訂正が来る。
相手の気持ちの判定にはならない（恋亀にどう見えたか、までにする）。
`prompt.ts` の `NEVER` も「わたしはそう感じる」までは許している。

**毎回「みんなはどう？」を付けない。** それは定型の煽りになる。
言い切りで終わる型（違和感）があってよい。問いは文中にあれば足りる。

### 4.1.3 時間帯で、型を寄せる

テーマは縛らない（縛ると夜のテーマが朝に出せなくなって同じ話が続く）が、
型は寄せる。`persona.posting.slot_category_weights`。

| 枠 | A 共感 | B 問い | C 恋亀 | D 告知 |
|---|---:|---:|---:|---:|
| 朝 08:00 | 61% | 18% | 17% | 3% |
| 昼 12:30 | 40% | 27% | 14% | **18%** |
| 夜 21:00 | 32% | **48%** | 15% | 4% |

夜のほうが手が止まるので、返信の来る問いを夜に厚くする。
告知は昼だけ——朝は読み飛ばされ、夜は売り込みが目立つ。

> 生成は夜22時の1回で3本積むので、**生成時刻から枠は判定できない**。
> ワークフローが `--slot morning|noon|night` を渡し、積んだ順に出る。

### 4.2 型（ブリーフ8をそのまま）

| 型 | 使う所 | 芯 |
|---|---|---|
| 1 二択 | A・B | 選ばせる。選んだ人はコメントしやすい |
| 2 違和感 | A | **「分からない」を言語化する。いちばん強い型**（§1） |
| 3 男女差 | B | 聞く。代弁しない |
| 4 恋亀実演 | C | 続きから始まる体験を見せる |
| 5 人間の反応 | C | AI と人の線を引く。**確カメるの入口** |

### 4.3 C と D は、いま売れるもので書く

§0.1 のとおり、音声の鍵が入るまで「恋亀に話す」は書けない。

**鍵が入るまでの C・D**（確カメるを主語にする）

```
C  「このLINE、自分では3回読み返した。
     でも自分の目でしか読めてない。
     実際に女性が読んだら、どこで引っかかるんやろ🐢」

D  「送る前の文面を、実在する女性に読んでもらえます🐢
     判定と、そう感じた理由が返ってくる。
     （住所）」
```

**鍵が入ったあとの C・D**（ブリーフの例をそのまま使える）

```
C  「デート帰りに恋亀に話すと
     🐢『前回、水族館の日程決めるところやったよね。どうなった？』
     って続きから始まる。毎回説明しなくていいの、地味に楽。」
```

> C の例文は `src/lib/koi/demo.ts` の `DEMO_TALK` と揃える。
> トップで見せている会話と、Threads で見せる会話が違うと、
> 来た人が「さっきのと違う」になる。

### 4.4 公開審議（週1・シリーズ）

ブリーフ18の「恋亀の継続審議」「男女で割れました」を、**週1の定点**にする。

```
月  B で問いを出す（リンク無し）
火〜水  コメントが集まる
木  「割れました」で返す🐢
     ・どっちが多かったか
     ・割れた理由
     ・恋亀はまだ継続審議
```

これが効く理由は3つ。

1. **返信が増える** — 2026年のアルゴリズムで最重要の指標
2. **思想の実演になる** — 「人によって感じ方が違う」を、説明せずに体験させる
3. **リンクが要らない** — 露出が落ちない

**シリーズは増やしすぎない。** 2本まで（ブリーフ18）。

## 5. 送客は、投稿ではなくプロフィール

ブリーフ19のとおり、毎投稿に URL を貼らない。

```
A・B・C（90%）  リンク無し  →  「この亀なんなん」  →  プロフィール
D（10%）        リンク有り  →  直接
```

**だから `utm_medium=profile` が主導線になる。**
いまの `hypotheses.json` は投稿内リンク（`utm_medium=social`）しか持っていない。
プロフィール側に UTM を付けないと、**効いている導線が丸ごと計測から消える。**

## 6. 量と、人の時間

ブリーフ16は初週に **1日5〜8投稿・20〜30返信**。
**これは自動化の話ではなく、人の時間の話。**

| | 時間/日 | 自動化 |
|---|---|---|
| 投稿3〜8本（A・B・C） | 0分 | **◯ 全自動** |
| D（告知）の承認 | 週2本・5分 | ✕ 人 |
| **他人の投稿への返信20〜30件** | **60〜90分** | **✕ 人** |
| 自分の投稿への返信 | 15分 | **✕ 人** |

**1日1時間15分〜1時間45分。ほぼ全部が返信。**
30日続く量かどうかを、始める前に決める。

続かないなら、**本数ではなく返信を残す。** 本数は自動なので減らしても
時間は浮かないが、返信は時間がそのまま効き、いちばん表示数を動かす。

### 返信を自動化しない理由

**技術的には、できなくはない。** 先に正確に書く。

- `POST /{user-id}/threads` の `reply_to_id` は、他人の投稿のIDでも通る
  （`core/poster.py` の `create_thread_post`。連投に使っているのと同じ口）
- 返信する相手を**探す**ほうに壁がある。`threads_search` は
  `threads_keyword_search` 権限が要り、これは Meta のアプリレビューを通さないと
  使えない。いま未承認（`THREADS_KEYWORD_SEARCH_APPROVED` が空）

そのうえで、**通っても自動化しない。**

- **規約** — 面識のない人の投稿に機械で返信を配るのは、本文の自動投稿とは別の線。
  アカウントを失うと、積み上げたものが全部消える
- **ブランド** — 「実在の人が読む」を売っている。恋亀の返信が機械だと、
  商品そのものの嘘になる。しかもいちばん人格が出る場所で嘘をつくことになる
- **効き目** — ブリーフ9のねらいは「この亀なんなん」を作ること。
  定型文を配っても、そうはならない

→ **返信は Threads アプリで手でやる。** ここは設計から外す。

### 承認ゲートは外さない。ただし型で分ける

`immediate_posting_forbidden = true` のまま。ゲートそのものは残す。
外すと、止めたいときに止める口が無くなる。

そのうえで、**危なさは一様ではない**ので、型で分ける。

| 型 | 承認 | なぜ |
|---|---|---|
| A 共感 / B 問い / C 恋亀 | **自動** | リンクも商品の話も持たない。外しても滑るだけ |
| D 告知 | **人** | URLを貼ってサービスの話をする。書き方を1つ間違えると、**できないことを売る**（§0.1） |

Dは全体の1割＝**週に2本ほど**。ここだけ人が見ても手間は小さい。

歯止めは3つ（`persona.posting.posting_types.automated.auto_approve`）。

- `max_per_day` — 1日に自動で通す上限（5本）。生成が暴走したときの最後の歯止め
- `max_pending_approved` — 投稿待ちが溜まったら自動承認を止める（10本）。
  投稿側が詰まっているのに生成だけ進むと、古い投稿が後から出る
- `accounts/<id>/KILL_SWITCH` — ファイルを1つ置けば全部止まる。設定を触らなくてよい

自動で通したものは `decided_by: "auto"` が残る。人が押したものと混ざらないので、
あとから「これ誰が通した？」に答えられる。

### 本数は上げていく

```
1〜2週目   1日3本（A1・B1・C1）＋ 返信20件
3〜4週目   1日5本            ＋ 返信30件
5週目〜    勝ち筋が分かってから増やす
```

初日から8本にしない。**人格が固まる前に量を出すと、ブレた恋亀が量産される。**

## 7. 見る数字

ブリーフ14の順をそのまま採る。**フォロワー数は最重要にしない。**

| 順 | 数字 | どこから |
|---|---|---|
| 1 | 返信率 | `history.json` → `reports/weekly.md` |
| 2 | プロフィール閲覧 | `account_metrics.json`。**API にあるか未確認**（下記） |
| 3 | サイトのクリック | `site_landed` の `utm_medium=profile` |
| 4 | 恋亀開始 | `koi_started` |
| 5 | 初回完了 | `koi_completed` |
| 6 | 2回目 | `koi_returned` |
| 7 | 課金 | `purchase_paid` |

> **2番だけ、取れるか分からない。** Threads の Insights に `profile_views` が
> あるかを確かめられていない（トークンが別リポジトリの Secrets にあり、
> ここから叩けない）。`profile_views` / `clicks` / `link_clicks` を**1つずつ別の
> 呼び出しで**試して、通ったものだけ残す。混ぜて投げると、名前が1つ違うだけで
> フォロワー数まで取れなくなる。
>
> 取れなければ、3番（`utm_medium=profile` の着地）で代わりにする。
> 見られただけで押されていないプロフィールは、どのみち効いていない。

### 投稿の評価（ブリーフ15）

バズを成功としない。

```
10万表示 → クリック10      低く評価
 3千表示 → クリック50 → 恋亀開始15   高く評価
```

**これを成立させるには、投稿単位で下流まで追えなければならない。**
`utm_content` に投稿ごとの追跡コードを入れてある（§9）。

### 学習ループ（実装済み・2026-10-03）

投稿の自動化は動いている。足りなかったのは、**結果が次の投稿に返る経路**。

```
毎朝  collect   Threads API → 投稿ごとの表示数・返信数     → history.json
                アカウント全体（フォロワー・表示数ほか）  → account_metrics.json
毎朝  report    直近7日を集計                              → reports/weekly.md（上書き）
```

`reports/weekly.md` が持つもの:

- **型べつ**（型1〜5 と D）の表示数と返信率
- **カテゴリべつ**（A/B/C/D）
- **テーマべつ**（13個）
- **アカウント全体**のフォロワー・表示数の増減
- **`utm_content` → 投稿 の対応表**

最後の1つが、サイト側（`events` テーブルの着地・購入）と繋ぐ鍵。
Vercel 側の数字は Threads からは見えないので、コードで突き合わせる。

日付つきのファイルを増やさず、1枚を上書きする。推移は git の履歴が持つ。

```
python -m core.main report mens-body-lab --days 7
git log -p apps/threads/reports/weekly.md
```

**平均ではなく中央値を出す。** 1本バズると平均が持ち上がって、他が全部
「平均以下」になる。返信率も投稿ごとに出してから中央値を取る
（合計÷合計にすると、表示数の大きい1本の率が全体の率になる）。

**数字を出すだけで、設定は書き換えない。** 止める判断は人がする。
5本に満たない束には「判断できる本数ではない」と出る。

**見る順番を固定する。** リプライが多くても買われない型があり、
静かでもサイトまで連れてくる型がある。

1. **表示数** — 読まれているか
2. **リプライ率** — 会話になっているか（＝次も表示されるか）
3. **着地率** — リンクが押されているか
4. **購入率** — 金を払う人の話だったか

**3と4で止める判断はしない。** 母数が溜まるまでは1と2で回す。
少ない本数で切ると、効くものを先に捨てることになる。

## 10. この設計が前提にしていること

外れたら、設計ごと見直す。

1. **恋亀は、キャラクターとして好かれうる** — 好かれないなら、
   どれだけ投稿しても「自分の話も聞いてほしい」にならない
2. **1日2時間の手作業が30日続く**（§6） — 続かないなら本数を落とす。
   本数より**返信**を残す
3. **無料の恋亀から、有料の確カメるへ渡る**（`koi_to_ask`） — 渡らないなら、
   恋亀は良い広告で終わる。Phase 2 でここを最初に見る
4. **音声の鍵と住所が決まる**（§0） — 決まらないなら、
   ブリーフの導線は後半が無いまま走ることになる

## 11. 何を自動化し、何をしないか

| | 自動 | 理由 |
|---|---|---|
| 生成 | ◯ | 型が決まっている |
| **A・B・C の承認** | ◯ | リンクも商品の話も持たない |
| 投稿 | ◯ | 枠が決まっている |
| 数値の収集 | ◯ | API で取れる |
| テーマの配分 | ◯（週次） | 数字で決まる |
| **D（告知）の承認** | ✕ | できないことを売らないため。週2本 |
| **自分の投稿への返信** | ✕ | 規約とブランド |
| **他人の投稿への返信** | ✕ | 規約とブランド（技術的には可能。上記） |
| **公開審議の選定** | ✕ | 人の文面を扱う。事故が取り返せない |

**投稿は人手ゼロで回る。** 人が触るのは、週2本のDと、返信だけ。

**自動化の目的は、人の時間を「返信」に寄せること。**
ブリーフ9の「他人の投稿への返信」が、この設計でいちばん効く手で、
いちばん自動化してはいけない。
